# 02 需求规格（DCE 2.0 缺陷闭环）

## 1. 角色与边界

| 角色 | 负责 |
|---|---|
| 用户（开发负责人） | 两个确认点（G1 修复方案、G2 合并）；切换测试账号；执行 SQL、改 Nacos/菜单权限；对“是否算通过”有最终解释权 |
| Host Agent（Cursor / Codex） | 读缺陷、定位与修改代码、本地编译测试、自审、浏览器测试、写修复记录、按 Playbook 编排各步骤 |
| DCE（本项目） | 持有平台凭证；读禅道缺陷（含图片）；根据代码改动生成部署计划；合并到测试分支；触发并跟踪 CI；Portainer 拉镜像更新并核对 digest；把缺陷标记为已解决；记录运行状态以便跨会话恢复 |

DCE 不理解业务、不改业务代码、不操作浏览器、不判断测试是否通过。

## 2. 闭环步骤与 DCE 支撑

| 步骤 | 谁做 | 用到的 DCE 能力 | 完成标志 |
|---|---|---|---|
| S0 恢复现场 | Agent | `dce_status` | 知道有没有未完成的 run、当前阶段 |
| S1 读缺陷 | Agent | `bug_list`、`bug_get`（含图片、历史） | 缺陷正文、图片、重开历史都已读到 |
| S2 分析/方案 | Agent，必要时 G1 | — | 方案清楚；不清楚的已问用户 |
| S3 修复 | Agent | — | 改在特性分支上；本地能编译；提交信息带 `bug#<ID>` |
| S4 自审 + 部署计划 | Agent | `deploy_plan` | 自审清单过完；部署计划表生成 |
| S5 合并确认 G2 | 用户 | — | 用户明确同意合并 |
| S6 合并 | DCE | `merge_to_test` | 特性分支已推送；测试分支已合并并推送 |
| S7 编译构建 | DCE | `ci_build`、`ci_status` | 计划内的 compile/build 全部成功，拿到镜像 digest |
| S8 部署 | DCE | `service_deploy`、`service_status` | 服务任务全部运行，运行镜像 digest 等于构建 digest |
| S9 测试 | Agent，必要时用户配合 | `service_status`（日志尾部）、`run_update` | 每个缺陷有通过/不通过结论和截图；不通过回到 S3 |
| S10 记录 | Agent | `dce_status`（取提出/修复时间）、`run_update` | 修复记录已更新并推送 |
| S11 禅道 | DCE | `bug_resolve` | 缺陷状态为已解决、指派回提测人、备注含修复与验证摘要 |

一次 run 可以包含多个缺陷（用户常一次处理几个），一起合并、构建、部署，分别记录和解决。

## 3. 功能需求

### P0（本期必须）

- **R1 初始化（project_setup scan）**：一条命令扫描业务工作区，生成 `.dce/dce.yaml` 草稿：
  - 列出全部 Git 仓库，解析 GitLab 项目 ID；
  - 从各仓库测试分支的 `.gitlab-ci*.yml` 解析出测试分支名、模块路径、compile/build job、镜像名（支持 `extends`、变量展开、`trigger` 子流水线）；
  - 在 Portainer 中按镜像仓库路径精确匹配服务，推断测试环境 Stack、Swarm ID、私有仓库 registryId；
  - 从 pom 推导库模块与下游模块的依赖；
  - 找到已有的缺陷修复记录文件。
  - 不确定的字段写 `# TODO(确认)` 注释，由用户在编辑器里改。已有配置不覆盖，另写 `dce.proposed.yaml` 并给出差异。
- **R2 自检（project_setup check）**：逐项检查配置、仓库、分支、job、服务、镜像、凭证可用性，输出 pass/warn/fail 和修复提示。全部 pass（或只剩“写权限待首次使用验证”的 warn）即初始化成功。
- **R3 缺陷读取**：按配置的禅道产品列出“指派给我、激活”的缺陷；读单个缺陷的正文、附件图片（作为 MCP 原生图片返回）、操作历史（含重新激活）。产品不符直接拒绝，不返回正文。不需要按 Bug 维护白名单。
- **R4 部署计划**：给定缺陷 ID（和可选的仓库列表），对比各仓库特性分支与测试分支：
  - 列出将被合并的提交；
  - 把改动文件映射到模块，得到 job、镜像、服务；
  - 库模块改动时列出依赖它的下游模块（标“建议重编”）；
  - 给出无法归属的改动、工作区不干净、未推送、正在测试分支上改代码、测试分支代码混进特性分支等警告；
  - 按依赖顺序输出“打包部署顺序表”。
- **R5 合并到测试分支**：在临时 worktree 中完成，不动用户当前检出。先推特性分支，再把 `origin/<特性分支>` 以 `--no-ff` 合入 `origin/<测试分支>` 并普通推送。冲突时中止并返回冲突文件。只允许配置里的测试分支；永不 force push；永不触碰 master/main/release*/prod*/uat*。
- **R6 编译构建**：找到合并提交对应的流水线（含子流水线），只 play 计划内的手动 compile job；job 不存在时（`changes` 规则未命中，例如只改了上游库）在测试分支上新建一条流水线再找；跟踪 compile→build，build 成功后从 Trace 解析推送的镜像 digest；失败时区分“基础设施失败”和“代码失败”，附 Trace 尾部。
- **R7 部署与核验**：只有 build 成功的服务才允许部署。调用 Portainer 强制更新并重新拉取镜像（带 registryId）；按依赖顺序执行；核验所有任务运行中、运行镜像 digest 等于构建 digest；失败时返回任务错误和日志尾部。
- **R8 运行记录**：每个 run 一份 JSON，记录计划、合并 SHA 与时间、流水线与 job、digest、部署前后镜像、测试结论与截图路径、修复记录提交、禅道结果、审计事件。新会话可以从中恢复。
- **R9 禅道已解决**：前置条件为测试通过且修复记录已提交。调用禅道 v1 解决接口（resolution=fixed，解决版本 trunk，指派回提测人），备注自动汇总修复提交、合并时间、部署 digest、验证结论。完成后复读确认状态。已解决的跳过。
- **R10 Playbook**：一份 Skill（Cursor 和 Codex 通用），规定 Agent 的标准步骤、两个确认点、人工停点、浏览器测试规范、修复记录模板、提交信息规范和自审清单。

### P1（本期可选）

- 测试分支代码反向混入特性分支的精确检测（P0 只做简单警告）。
- 一次 run 内对多个特性分支（不同版本）的支持。
- 前端产物指纹核对（对比部署后的 JS bundle 哈希）。

## 4. 人工停点（Agent 必须停下来问）

- G1、G2 两个确认点。
- 需要切换测试账号、执行 SQL、修改 Nacos/环境变量/菜单权限、重启非计划内服务。
- 合并冲突、CI 基础设施失败（runner、镜像拉取超时）、部署后任务反复失败。
- 缺陷描述与参照系统（如“对齐某某平台”）理解不一致。
- 任何预发/生产相关操作。

## 5. 非功能要求

- **可用性**：初始化 scan 在约 20 个仓库的工作区 2 分钟内完成。不含等待的工具调用 30 秒内返回；含等待的调用（`ci_build` 等待流水线创建、带 `wait_seconds` 的轮询）内部等待不超过 45 秒，整体不超过 55 秒。
- **可诊断**：错误必须带具体原因和下一步提示（例如“GitLab 返回 403：令牌缺少 api 权限，请在 credentials 中换成 api scope 的 Token”），禁止把不同故障折叠成同一句话。
- **输出精简**：每个工具返回 `summary`（给人看的一句话或表格）+ `data`（结构化）+ 可选 `warnings`/`next`。默认文本输出不超过 24KB；图片单独计算。
- **安全**：凭证只在 DCE 进程内；输出和日志脱敏；写接口白名单写死在代码里；目标必须在配置内；所有写操作写审计事件（见 03 第 7 节）。
- **兼容**：Python 3.12；MCP stdio；同一服务层同时提供 MCP 工具和 CLI 命令。

## 6. 成功标准

1. 在真实业务工作区，初始化 scan + 用户少量修改 + check 全部通过，用时不超过 15 分钟（含人工确认）。
2. 用一个真实缺陷，从 `bug_get` 到 `bug_resolve` 完整跑通。用户只在 G1/G2 和必要的人工停点介入；GitLab、Portainer、禅道三处零手工点击。
3. 部署计划表与用户过去手写的“打包部署顺序表”一致，库改动时下游服务不漏。
4. 全程 Agent 没有读取浏览器 Cookie、localStorage 或任何平台 Token。
