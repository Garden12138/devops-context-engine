# 06 验收标准

两类验收缺一不可。离线验收证明代码按设计工作，现场验收证明闭环在真实平台上能用。1.x 的教训是只有前者，所以本版**每个里程碑都要过现场验收**才算完成。

## 1. 离线验收（每个任务和里程碑）

| 项 | 命令 | 标准 |
|---|---|---|
| 单元与集成测试 | `uv run pytest -q --cov` | 全部通过；`dce.workspace`、`dce.loop`、`dce.platforms` 覆盖率 ≥ 80% |
| 静态检查 | `uv run ruff check .`、`uv run mypy` | 无错误 |
| 公开数据检查 | `.venv/bin/python scripts/check_public_data.py` | 无私有地址、无 Token |
| MCP 冒烟 | `tests/test_mcp_stdio.py` | 12 个工具可列出，已实现的工具可调用 |
| 写接口白名单 | `tests/test_http_write.py` | 白名单外的请求一律在发出前被拒 |
| 不使用 force | `tests/test_merge.py` | git 调用记录中没有 `--force`/`-f` |

结果写进 `docs/v2/progress.md`，一行一个任务：日期、任务、提交、测试数与覆盖率。

## 2. 现场验收（每个里程碑一次）

由用户在 Cursor（或 Codex）里，在真实业务工作区执行。结果写进 `docs/v2/progress.md`，只写 PASS/FAIL、耗时和不含真实名称的简短说明；真实细节写在本机 `.local/v2/acceptance-notes.md`。

### 共同前置

1. 凭证文件放在 `~/.config/dce/credentials.env`（0600），GitLab 令牌带 **api** scope，Portainer API Key 的用户对测试 endpoint 有服务更新权限。
2. 在业务工作区新增 `.cursor/mcp.json`（格式见 03 第 3.4 节），并删除全局 `~/.cursor/mcp.json` 中旧的 `dce` 条目，然后重载 MCP，确认只有一个 DCE 进程、12 个工具。
3. Cursor 的 MCP 自动运行：除 `merge_to_test` 外都可以自动运行。

### R1 初始化（M1）

| 步骤 | 操作 | 通过标准 |
|---|---|---|
| 1 | 对话中说“初始化 DCE” | Agent 调用 `project_setup(scan)`，2 分钟内返回 |
| 2 | 看汇总表 | 列出全部业务仓库与 GitLab ID；每个部署模块都匹配到服务，或有明确的 TODO 说明原因 |
| 3 | 在编辑器里处理 TODO | 测试分支（含例外仓库）、Stack、修复记录文件与用户认知一致 |
| 4 | 说“检查 DCE 配置” | `project_setup(check)` 没有 fail；warn 只剩写权限待首次使用 |
| 5 | 故意把一个 job 名改错再 check | 报出具体是哪个仓库、哪个 job、在哪个 CI 文件里找不到 |

整体耗时（含人工修改）不超过 15 分钟。

2026-11-17 本次 R1 例外：用户报告已执行操作清单第 1–6 步，要求跳过第 7 步（对应上表第 5 步的故意改错 job 自检）。该负向现场检查予以豁免，具体错误定位继续由离线测试覆盖。现场自检结果和耗时确认后记录本次 R1 结论。

### R2 缺陷与部署计划（M2）

| 步骤 | 操作 | 通过标准 |
|---|---|---|
| 1 | “列出我的禅道缺陷” | 数量与禅道页面“指派给我、激活”一致 |
| 2 | 打开一个带截图的缺陷 | Agent 能正确描述截图内容（证明图片真的到了模型） |
| 3 | 读一个其他产品的缺陷 | 返回 `OUT_OF_SCOPE`，没有正文 |
| 4 | 选一次已完成的历史修复，对其提交范围生成部署计划 | 表格与用户当时手写的“打包部署顺序表”一致；涉及公共库时，下游服务被列为“建议重编” |
| 5 | 在工作区留一个未提交改动后再生成计划 | 出现 `DIRTY` 警告 |

### R3 合并与构建（M3）

用一个真实的小缺陷（或用户指定的无害改动）。

| 步骤 | 操作 | 通过标准 |
|---|---|---|
| 1 | Agent 给出 G2 材料 | 包含 diff 摘要、自审结论、部署计划表 |
| 2 | 用户同意，调用 `merge_to_test` | Cursor 弹出确认；测试分支出现合并提交；用户本地检出的分支和文件不变 |
| 3 | `ci_build` 后轮询 `ci_status` | 只触发计划内的 compile job；build 自动跟随；拿到镜像 digest |
| 4 | 制造一次冲突（可选） | 返回冲突文件，测试分支未被修改 |

### R4 部署与核验（M4）

| 步骤 | 操作 | 通过标准 |
|---|---|---|
| 1 | 构建未完成时调用 `service_deploy` | 该服务被跳过（`skipped`，原因“构建未完成”），没有发出更新请求 |
| 2 | 构建完成后部署 | 服务开始滚动更新 |
| 3 | `service_status(wait_seconds=45)` | 判定 `converged`；运行 digest 等于构建 digest |
| 4 | `logs_tail=100` | 返回最近日志，无凭证泄露 |
| 5 | 在 Portainer 页面核对 | 服务更新时间、镜像与 DCE 报告一致 |

### R5 完整闭环（M5）

用一个真实缺陷，在一个新对话里只说：“处理禅道缺陷 <ID>”。

通过标准：

1. Agent 按 Playbook 走完 S0–S11；用户只在 G1（如果需要）、G2 和必要的人工停点（切账号、SQL 等）介入。
2. GitLab、Portainer、禅道三处，用户和 Agent 都没有通过浏览器手工操作。
3. 修复记录文档新增该缺陷的汇总行和小节，含提出时间、修复时间（合入测试分支的时间）、验证说明和截图，并已推送。
4. 禅道中该缺陷状态为“已解决”，指派给提测人，备注含修复提交、部署 digest 和验证摘要。
5. 对话记录中没有读取浏览器 Cookie、localStorage 或平台 Token 的操作。
6. 在一个新对话里说“继续 run <ID>”，Agent 能通过 `dce_status` 恢复到正确阶段。

## 3. 旧痛点回归清单

现场验收期间逐条确认：

| 1.x 时期的问题 | 2.0 的对策 | 在哪里验证 |
|---|---|---|
| 用户反复下“提交、合并、给部署顺序”的指令 | `deploy_plan` + `merge_to_test` | R2、R3 |
| 某仓库测试分支例外、后来又变了 | `dce.yaml` 的 `test_branch`，改文件即生效 | R1 |
| 用户找不到要点的 compile job | `ci_build` 自动定位并 play | R3 |
| 只 retry 了 compile，build 没跑，镜像是旧的 | 旧构建判定 | R3 |
| 镜像还没构建完就去 Portainer 更新 | 部署前置条件 | R4 |
| 改了公共库，漏列下游服务 | 计划中的“建议重编” | R2 |
| 每个新 Bug 都要改白名单并重启 | 按产品授权 | R2 |
| `INVALID_PAYLOAD` 一句话，不知道原因 | 具体错误信息 | R1 第 5 步 |
| 新旧两个 DCE 进程并存 | 只用项目级 `.cursor/mcp.json` | 共同前置 |
| Agent 读浏览器 JWT/Cookie 去调平台接口 | DCE 写工具 + Playbook 禁令 | R5 |
| 直接在测试分支上改代码 | `COMMITTED_ON_TEST_BRANCH` 警告，合并时拒绝 | R2 |
