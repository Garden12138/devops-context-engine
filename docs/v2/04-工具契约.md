# 04 工具契约（MCP 12 个工具 + CLI）

通用约定：

- 所有工具都有可选参数 `workspace`（绝对路径），解析规则见 03 第 3.4 节。下文不再重复。
- 返回结构见 03 第 10 节：`ok / summary / data / warnings / next`，失败时为 `ok=false / error`。
- 工具描述（MCP `description`）每个不超过 300 字，只写“做什么、何时用、前置条件”，不写治理条款。
- 读工具：`project_setup(check)`、`dce_status`、`bug_list`、`bug_get`、`ci_status`、`service_status`。
  写工具：`project_setup(scan)`（只写本地 `.dce/`）、`deploy_plan`（只写 run）、`merge_to_test`、`ci_build`、`service_deploy`、`run_update`（只写 run）、`bug_resolve`。

| # | 工具 | 闭环步骤 | 宿主自动运行建议 |
|---|---|---|---|
| 1 | project_setup | 初始化 | 可自动 |
| 2 | dce_status | S0 恢复 | 可自动 |
| 3 | bug_list | S1 | 可自动 |
| 4 | bug_get | S1 | 可自动 |
| 5 | deploy_plan | S4 | 可自动 |
| 6 | merge_to_test | S6（G2 之后） | **不要自动，宿主每次弹窗确认** |
| 7 | ci_build | S7 | 可自动 |
| 8 | ci_status | S7 | 可自动 |
| 9 | service_deploy | S8 | 可自动 |
| 10 | service_status | S8/S9 | 可自动 |
| 11 | run_update | S9/S10 | 可自动 |
| 12 | bug_resolve | S11 | 可自动 |

---

## 1. project_setup

扫描工作区生成配置（scan），或检查配置是否可用（check）。

输入：

```json
{"action": "scan" | "check"}
```

scan 输出 `data`：

```json
{"written": ".dce/dce.yaml",
 "proposed": false,
 "repos": [{"name": "demo-cloud", "gitlab_id": 12, "test_branch": "develop_v2", "modules": 5, "services_matched": 5, "todos": 1}],
 "environment": {"endpoint": 1, "stack": "demo_test", "swarm_id": "abc123def456", "registry_id": 2},
 "records_file": "demo-pm/projects/demo/V1.2.0/缺陷修复记录.md",
 "todos": [{"path": "repos[1].test_branch", "reason": "远端同时存在 develop 与 develop_v2"}],
 "diff": null}
```

`summary` 为仓库汇总表，以及“请在编辑器中处理 N 个 TODO(确认)，然后调用 project_setup(check)”。已有 `dce.yaml` 时，`written` 为 `.dce/dce.proposed.yaml`，`proposed=true`，`diff` 列出新增/删除/变化项。

check 输出 `data`：

```json
{"passed": false,
 "checks": [
   {"id": "config.schema", "status": "pass"},
   {"id": "gitlab.token_scope", "status": "fail", "detail": "令牌 scopes=[read_api]", "fix": "换成带 api scope 的令牌"},
   {"id": "repo.demo-cloud.test_branch", "status": "pass"},
   {"id": "repo.demo-cloud.job.compile_demo_order", "status": "pass"},
   {"id": "service.demo_test_demo-modules-order", "status": "pass", "detail": "镜像路径一致"},
   {"id": "portainer.write", "status": "warn", "detail": "写权限需首次部署时验证"},
   {"id": "zentao.resolve", "status": "warn", "detail": "解决权限需首次使用时验证"}]}
```

`passed = true` 的条件：没有 `fail`。检查项清单见 05 的 M1。

## 2. dce_status

不访问平台，只读本地配置和 run。

输入：`{"run_id": "可选"}`

输出 `data`：

```json
{"config": {"name": "demo-platform", "repos": 4, "environment": "test", "stack": "demo_test",
            "gates": {"fix_plan": "when_unclear", "merge": "always"}},
 "runs": [{"run_id": "20261113-1530-4336", "bugs": [4336], "stage": "deployed", "updated_at": "..."}],
 "run": null,
 "record_facts": null}
```

传入 `run_id` 时，`run` 为完整 run JSON（超过预算时省略 `events`，只保留最近 20 条），`record_facts` 为写修复记录所需的数据：

```json
[{"bug": 4336, "title": "...", "severity": 2, "pri": 2, "opened_at": "2026-11-12 10:47",
  "fixed_at": "2026-11-13 15:42", "verified_at": "2026-11-13 16:30",
  "repos": ["demo-cloud"], "commits": ["abc1234 fix(order): ... bug#4336"],
  "evidence": ["assets/4336-列表显示正常.png"]}]
```

## 3. bug_list

输入：

```json
{"scope": "mine" | "all", "status": "active" | "resolved" | "all", "limit": 20}
```

默认 `mine` + `active`。输出 `data.bugs`：

```json
[{"id": 4336, "title": "...", "severity": 2, "pri": 2, "status": "active", "type": "codeerror",
  "module": "模板管理", "opened_by": "tester01", "opened_at": "2026-11-12 10:47",
  "assigned_to": "dev01", "run_id": null}]
```

`summary` 为 Markdown 表格。

## 4. bug_get

输入：`{"bug_id": 4336, "images": true, "max_images": 6}`

输出 `data`：

```json
{"id": 4336, "title": "...", "status": "active", "severity": 2, "pri": 2, "type": "codeerror",
 "module": "模板管理", "opened_by": "tester01", "opened_at": "...", "assigned_to": "dev01",
 "steps_text": "【步骤】... 【结果】... 【期望】...",
 "images": [{"index": 0, "name": "file-read-901.png", "delivered": true}],
 "history": [{"date": "...", "actor": "tester01", "action": "activated", "comment": "仍然存在..."}],
 "run_id": null}
```

另附 `delivered=true` 的图片作为 ImageContent。缺陷不属于配置产品时返回 `OUT_OF_SCOPE`，不返回任何正文。

## 5. deploy_plan

输入：

```json
{"bug_ids": [4336, 4327],
 "repos": ["demo-cloud", "demo-web"],
 "feature_branches": {"demo-cloud": "feature/1.2.0"},
 "run_id": null,
 "add_items": [{"repo": "demo-cloud", "module": "demo-modules/demo-setup", "reason": "共享枚举改动"}],
 "drop_items": ["demo-cloud:demo-modules/demo-report"]}
```

除 `bug_ids` 外都可选。传 `run_id` 时刷新该 run 的计划（例如测试失败修复后再次合并前）。

输出 `data`：

```json
{"run_id": "20261113-1530-4336-4327",
 "items": [ "...同 03 第 4 节 plan.items..." ],
 "order": ["demo-common:demo-common-core", "demo-cloud:demo-modules/demo-order"],
 "commits": {"demo-cloud": [{"sha": "abc1234", "subject": "fix(order): ... bug#4336", "bugs": [4336]}]},
 "unmapped": {"demo-cloud": ["pom.xml"]},
 "bugs_without_commits": [4327]}
```

`summary` 为“打包部署顺序表”（格式见 03 第 6.1 节）。常见 warnings：`DIRTY`、`UNPUSHED`、`COMMITTED_ON_TEST_BRANCH`、`UNMAPPED_CHANGES`、`TEST_BRANCH_MERGED_INTO_FEATURE`、`BUGS_WITHOUT_COMMITS`（某缺陷号在提交信息里找不到）。

## 6. merge_to_test

输入：

```json
{"run_id": "20261113-1530-4336-4327", "repos": ["demo-cloud"], "approved_by_user": true}
```

`repos` 可选，默认取计划中的全部仓库。逐仓库执行 03 第 6.2 节的步骤，互不阻塞。

输出 `data.results`：

```json
[{"repo": "demo-cloud", "status": "merged", "feature": "feature/1.2.0", "test_branch": "develop_v2",
  "feature_sha": "abc1234", "merge_sha": "def5678", "merged_at": "2026-11-13T15:42:10+08:00"},
 {"repo": "demo-web", "status": "conflict", "files": ["src/views/order/index.vue"]}]
```

`status` 取值：`merged`、`already_merged`、`conflict`、`rejected`（守卫或前置条件不通过，附原因）、`push_rejected`。任何一个仓库不是 `merged`/`already_merged` 时，`ok` 仍为 true，但 `next` 提示先处理这些仓库。

## 7. ci_build

输入：`{"run_id": "...", "items": ["可选，计划条目 id"], "retry_failed": false}`

输出 `data.items`：

```json
[{"item": "demo-cloud:demo-modules/demo-order", "pipeline_id": 900, "child_pipeline_id": 901,
  "compile": {"id": 5001, "status": "pending", "action": "played", "web_url": "..."},
  "build": {"id": 5002, "status": "created"}}]
```

`action` 取值：`played`、`retried`、`already_running`、`already_succeeded`、`created_pipeline`、`missing`。

可以重复调用：每次只处理需要动作的 job（手动的 compile/build、`retry_failed=true` 时失败的 job、旧构建），见 03 第 6.3 节。

## 8. ci_status

输入：`{"run_id": "...", "wait_seconds": 30}`（0–45）

输出 `data`：

```json
{"overall": "building" | "succeeded" | "failed",
 "items": [{"item": "...", "compile": {"status": "success"}, "build": {"status": "success",
            "finished_at": "...", "digest": "sha256:..."}},
           {"item": "...", "build": {"status": "failed", "failure": "infrastructure",
            "trace_tail": "...最后 80 行，已脱敏..."}}]}
```

`ci_status` 只读，不触发 job。`next` 示例：全部成功时提示调用 `service_deploy`；build 停在手动或判定为旧构建时提示再调用 `ci_build`；有代码失败时提示回到修复；有基础设施失败时提示询问用户是否 `ci_build(retry_failed=true)`。

## 9. service_deploy

输入：`{"run_id": "...", "items": ["可选"]}`

输出 `data.services`：

```json
[{"service": "demo_test_demo-modules-order", "service_id": "x1y2z3", "status": "update_requested",
  "before_digest": "sha256:old...", "expected_digest": "sha256:new...", "method": "forceupdateservice"},
 {"service": "demo_test_demo-web", "status": "skipped", "reason": "构建未成功"}]
```

`method` 为 `forceupdateservice` 或 `docker_update`（回退方式）。

## 10. service_status

输入：

```json
{"run_id": "可选", "service": "可选，服务名，二选一", "wait_seconds": 30, "logs_tail": 0}
```

输出 `data.services`：

```json
[{"service": "demo_test_demo-modules-order", "verdict": "converged",
  "running": 1, "desired": 1, "running_digest": "sha256:new...", "expected_digest": "sha256:new...",
  "update_state": "completed", "task_errors": [], "logs": null}]
```

`verdict` 取值：`converged`、`updating`、`failed`、`digest_unverified`。`logs_tail > 0` 时 `logs` 为脱敏后的最近日志行（自部署时间起）。

## 11. run_update

输入（字段都可选，至少一项）：

```json
{"run_id": "...",
 "verification": {"bug_id": 4336, "result": "passed" | "failed", "notes": "列表 5G 模板正常显示，切换签名后刷新正确",
                  "evidence": ["demo-pm/projects/demo/V1.2.0/assets/4336-列表显示正常.png"]},
 "record": {"file": "projects/demo/V1.2.0/缺陷修复记录.md", "commit": "9f8e7d6"},
 "note": "用户已执行 SQL 恢复模板状态"}
```

规则：

- `result=failed` 时 run 阶段回到 `fixing`。
- `evidence` 路径必须在工作区内且文件存在，否则拒绝。
- `record.commit` 必须能在 records 仓库中用 `git cat-file -e` 找到。

## 12. bug_resolve

输入：`{"run_id": "...", "bug_ids": [4336], "comment": "可选，追加到自动备注末尾"}`

`bug_ids` 可选，默认取 run 中全部缺陷。前置条件和请求体见 03 第 6.5 节。

输出 `data.results`：

```json
[{"bug": 4336, "status": "resolved", "assigned_to": "tester01"},
 {"bug": 4327, "status": "blocked", "reason": "verification 未通过"},
 {"bug": 4300, "status": "skipped", "reason": "已是 resolved"}]
```

## CLI 对照

CLI 与工具共用 `loop/` 和 `workspace/`，输出相同的 JSON（加 `--pretty` 时输出 `summary` 文本）。

| 命令 | 对应工具 |
|---|---|
| `dce setup scan` / `dce setup check` | project_setup |
| `dce status [--run ID]` | dce_status |
| `dce bug list [--all] [--status S]` / `dce bug show ID [--save-images DIR]` | bug_list / bug_get |
| `dce plan BUG... [--repo R] [--run ID]` | deploy_plan |
| `dce merge --run ID --yes` | merge_to_test（`--yes` 对应 `approved_by_user`） |
| `dce build --run ID [--retry-failed]` | ci_build |
| `dce build-status --run ID [--wait 300]` | ci_status（CLI 可以等更久，内部循环） |
| `dce deploy --run ID` | service_deploy |
| `dce deploy-status --run ID [--wait 300] [--logs 100]` | service_status |
| `dce run update --run ID ...` | run_update |
| `dce resolve --run ID [--bug ID]` | bug_resolve |
| `dce mcp --connections F --credentials F [--workspace DIR]` | 启动 MCP stdio 服务 |

全局参数：`--connections`、`--credentials`、`--workspace`。缺省时依次读环境变量 `DCE_CONNECTIONS`、`DCE_CREDENTIALS`、`DCE_WORKSPACE`，再缺省为 `~/.config/dce/connections.toml`、`~/.config/dce/credentials.env`、当前目录。
