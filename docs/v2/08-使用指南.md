# 08 使用指南

DCE 连接禅道、GitLab 和 Portainer，在测试环境完成缺陷修复、构建部署、验证、记录和禅道解决。

## 安装

准备 Python 3.12 和 uv，在 DCE 仓库目录构建并安装固定版本的 wheel。

```sh
uv build --wheel
uv tool install --python 3.12 --force dist/devops_context_engine-2.0.0-py3-none-any.whl
dce --version
```

版本应显示 `2.0.0`。用 `uv tool dir --bin` 查询已安装命令的目录，在 MCP 配置中使用该目录下 `dce` 的绝对路径。以下示例用 `/Users/me/.local/bin/dce` 表示这个路径，`/abs/path/workspace` 表示包含业务 Git 仓库的工作区。

## 平台连接和凭证

在 `~/.config/dce/connections.toml` 配置三个平台的地址。仅当平台地址使用 HTTP 时设置 `allow_http = true`。

```toml
allow_http = true

[zentao]
base_url = "http://zentao.example.invalid/zentao"

[gitlab]
base_url = "http://gitlab.example.invalid"

[portainer]
base_url = "http://portainer.example.invalid:9000"
```

在 `~/.config/dce/credentials.env` 填写以下键，并执行 `chmod 600 ~/.config/dce/credentials.env`。

| 键 | 用途与权限 |
|---|---|
| `ZEN_USER`、`ZEN_PASSWORD` | 禅道账号和密码。账号可读取配置产品的缺陷，并解决指派给自己的缺陷。 |
| `GITLAB_TOKEN` | GitLab 个人访问令牌，带 `api` scope。 |
| `PORTAINER_API_KEY` | Portainer API Key，对测试 endpoint 有更新服务的权限。 |

## 连接宿主

### Cursor

在业务工作区创建 `.cursor/mcp.json`，替换 DCE 和配置文件的绝对路径，保留 `${workspaceFolder}`。

```json
{
  "mcpServers": {
    "dce": {
      "command": "/Users/me/.local/bin/dce",
      "args": [
        "mcp",
        "--connections", "/abs/path/user-config/dce/connections.toml",
        "--credentials", "/abs/path/user-config/dce/credentials.env",
        "--workspace", "${workspaceFolder}"
      ]
    }
  }
}
```

移除全局 `~/.cursor/mcp.json` 中旧的 `dce` 条目，重载 MCP，确认当前工作区只有一个 DCE 服务且列出 12 个工具。在 Cursor 的 MCP 自动运行设置里关闭 `merge_to_test` 的自动运行，每次在合并时确认宿主弹窗。

### Codex

在 `~/.codex/config.toml` 配置 MCP。替换 DCE 和配置文件的绝对路径，把 `--workspace` 后的值改为业务工作区的绝对路径，随后重新打开会话。

```toml
[mcp_servers.dce]
command = "/Users/me/.local/bin/dce"
args = [
    "mcp",
    "--connections", "/abs/path/user-config/dce/connections.toml",
    "--credentials", "/abs/path/user-config/dce/credentials.env",
    "--workspace", "/abs/path/workspace",
]
```

### 安装 Skill

用已安装的 `dce` 按正在使用的宿主选一条命令，并替换业务工作区路径。

```sh
# Cursor
dce install-skill --dest "/abs/path/workspace/.cursor/skills"
# Codex
dce install-skill --dest "/abs/path/workspace/.agents/skills"
```

已有不同版本时，先核对差异，再加 `--force` 安装。新开会话后，Playbook 会指导 Agent 在确认点暂停。

## 升级

1. 在新版本的 DCE 仓库目录运行 `uv build --wheel`，构建新版本的 wheel。
2. 运行 `uv tool install --python 3.12 --force <新版本 wheel 路径>`，再用 `dce --version` 核对版本。
3. 在 Cursor 重载 MCP。
4. 用已安装的 `dce install-skill --dest <Skill 安装目录>` 更新 Skill。有差异时先核对，再加 `--force` 安装。

## 初始化业务工作区

连接 MCP 后，在 Cursor 或 Codex 打开包含业务仓库的目录。下面以 `/abs/path/workspace` 为例，MCP 配置里的 `--workspace` 也应指向这个目录。

```text
/abs/path/workspace/
├── demo-web/    # 业务代码仓库
└── demo-pm/     # 修复记录仓库
```

1. **生成配置。** 在对话里说「初始化 DCE，扫描当前工作区」。Agent 会调用 `project_setup(action="scan")`。生成 `.dce/dce.yaml` 后，在编辑器打开它。如果已有配置，扫描会生成 `.dce/dce.proposed.yaml`，按返回的差异把需要的修改应用到 `.dce/dce.yaml`。
2. **核对并补齐配置。** 逐项处理 `TODO(确认)`，用实际环境中的值替换下面的示例值。

   - 核对禅道产品编号，例如 `zentao.product` 为 `100`。
   - 核对测试分支、CI job、测试集群与服务。例如 `demo-web` 用 `develop` 作为测试分支，GitLab 构建 job 是 `build_demo_web`，镜像部署到测试 Stack `demo_test` 下的 `demo_test_demo-web` 服务。
   - 确认现有修复记录的位置。例如 `records.repo` 是 `demo-pm`，`records.file` 是相对该仓库的 `projects/demo/缺陷修复记录.md`。
   - 填写测试入口，例如把 `environment.urls.main` 设为 `https://test.example.invalid/`，并在 `.dce/test-notes.md` 写一句「登录测试账号后，进入商品列表验证搜索功能」。

3. **运行自检。** 在对话里说「检查 DCE 配置」。Agent 会调用 `project_setup(action="check")`。看到 `passed=true` 就可以开始处理缺陷。如有 `fail`，按提示修正后再次自检。例如提示找不到 `build_demo_web` 时，先在 `demo-web` 的 CI 文件里核对实际 job 名。Portainer 更新权限和禅道解决权限在首次调用时验证。GitLab scope 查询返回 HTTP 404 时，在令牌设置中核对 `api` scope。

也可以在终端用以下命令扫描和自检。执行第二条前，先按上面的步骤修改配置。

```sh
dce --workspace "/abs/path/workspace" setup scan
dce --workspace "/abs/path/workspace" setup check
```

## 日常操作

### 处理一个缺陷

完成初始化并安装 Skill 后，在同一个业务工作区打开新会话。下面用缺陷 `12345` 演示，操作时换成你的实际禅道缺陷编号。

1. **发起处理。** 说「处理禅道缺陷 12345」。例如，缺陷描述为「商品列表清空搜索词后，列表没有恢复」。Agent 会读取缺陷正文和截图，定位 `demo-web` 中的相关代码。
2. **按需确认修复方案（G1）。** 如果缺陷描述有歧义、改动范围较大，或配置要求每次确认，Agent 会在改代码前说明根因、方案、影响范围及需要你配合的事项。核对后可以回复「确认，按这个方案修复」。
3. **确认合并和部署（G2）。** Agent 修复并自审后，会展示各仓库的改动、自审结果、部署计划和风险。比如计划是将 `demo-web` 的特性分支合入 `develop`，运行 `build_demo_web` 并更新测试服务 `demo_test_demo-web`。核对后回复「确认合并到测试分支并构建部署」，再在 Cursor 的 `merge_to_test` 弹窗里确认调用。
4. **查看验证结果。** 部署后，Agent 会在测试环境复现并验证，例如搜索商品后清空关键词，确认列表恢复。需要登录时，Agent 会停下来请你操作。验证通过后，Agent 会保存截图、提交并推送修复记录，再把禅道缺陷标记为已解决。默认指派给提测人，由测试人员关闭缺陷。

### 继续上一次处理

在同一业务工作区的新会话里，说「继续 run 20261120-1530-12345-1a2b3c4d」，把示例换成部署计划返回的 `run_id`。Agent 会调用 `dce_status(run_id)` 读取进度。例如，上次已完成部署（`deployed`），这次就从浏览器验证继续。

## 常见错误与处理

| 错误或状态 | 处理 |
|---|---|
| `WORKSPACE_REQUIRED`、`WORKSPACE_MISMATCH` | 核对 MCP 的 `--workspace`，将宿主打开的目录与工具实参对齐。 |
| `CONFIG_MISSING`、`CONFIG_INVALID` | 初次使用先 scan。已有配置时按提示修正相应的 YAML 字段，再运行 check。 |
| `CREDENTIALS_INVALID`、`AUTH_FAILED` | 按提示核对凭证文件路径、0600 权限、所需键及对应平台的连接与凭证。 |
| 禅道缺陷 `OUT_OF_SCOPE` | 核对缺陷和 `zentao.product`。 |
| `BUG_METADATA_UNAVAILABLE` 或 `BUG_METADATA_MISSING` | 写记录时按提示调用 `bug_get(bug_id, images=false)` 补齐快照缺失的字段。 |
| 合并冲突或推送被拒 | 查看对应仓库及原因，处理冲突或分支竞争后自审并重新确认合并。 |
| `CI_JOB_MISSING` 或构建失败 | 打开返回的流水线链接核对 job 规则。代码失败按 Trace 修复，基础设施失败按提示决定是否重试。 |
| 部署被跳过或 `digest_unverified` | 部署被跳过时核对本轮构建状态。返回 `digest_unverified` 时继续浏览器验证，并在汇报中说明镜像 digest 未能自动核对。 |
| 验证或记录更新失败 | 把截图保存到业务工作区内，核对 records 仓库与修复记录提交。 |
| 禅道解决接口返回 HTTP 4xx | 按返回的状态码和错误文字检查 `zentao.resolve.assign_to`、`zentao.resolve.resolved_build` 与解决权限。 |

现场操作见 [06 验收标准](06-验收标准.md#r5-完整闭环m5) 和 [07 Playbook](07-Playbook.md)。
