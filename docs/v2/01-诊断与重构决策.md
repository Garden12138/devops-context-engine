# 01 诊断与重构决策（ADR-2026-11-13）

状态：已决定（用户 2026-11-13 确认）。本文件解释为什么 DCE 从 1.2 重写为 2.0，以及哪些东西保留、哪些删除。实现细节见 03/04/05。

## 1. 用户真正要的是什么

用户在真实缺陷修复会话中亲手写过的闭环（原话整理）：

1. 修复禅道上的缺陷（读缺陷、审代码；需求不清先给方案）。
2. 推送特性分支，再合并到测试分支并推送（多数仓库是 `develop`，个别仓库例外，例外会变）。
3. 在 GitLab 编译打包改动涉及的服务（compile job 是手动触发，build 自动跟随）。
4. 在 Portainer 让对应服务重新拉取镜像并更新。
5. 在测试环境用浏览器验证；没通过就回到第 2 步，直到全部通过。
6. 更新缺陷修复记录文档（每个缺陷附截图、提出时间、修复时间），提交推送。
7. 在禅道把缺陷标记为“已解决”，指派回提测人。

DCE 2.0 的目标就是让 Agent 能稳定地跑完这 7 步，人只在两个确认点介入。

## 2. 1.x 为什么失败

| 现象（来自真实会话） | 根因 |
|---|---|
| “提交推送特性，合并到 develop……最后提供打包部署顺序列表”被用户重复约 30 次 | DCE 没有“改动 → 分支 → job → 镜像 → 服务”的部署计划能力 |
| GitLab 编译、Portainer 更新、禅道“已解决”靠用户手点，或 Agent 读浏览器里的 JWT/Cookie 去调接口 | 1.x 需求明确“不触发 CI、不 redeploy、不写禅道”，闭环最费时的三步被排除在外；Agent 只能绕道，反而更不安全 |
| `project.yaml` 1672 行、53 条关系，47 条长期 proposed，仍答不出“这个 Bug 跑哪个 job、更新哪个服务、去哪测” | 用“证据状态机 + 多对多关系图”建模本应是“约定表”的东西 |
| 初始化第一步 `project_context` 返回笼统 `INVALID_PAYLOAD`，begin/review/complete 全部无法开始 | Host Roots 绑定、本机审批页、receipt、hash 往返等多层仪式，每层都是故障点；错误被折叠成一句话 |
| 每修一个新 Bug 要改 `--zentao-bug` 白名单并重启 MCP | 授权粒度错误（按 Bug 而非按产品） |
| Agent 读 DCE 源码/排查进程的调用次数多于真正调用 DCE 的次数；10 个工具 Schema 合计约 120KB | 工具按平台原子 API 切分（32 个 operation），描述以治理条款为主，信封 11 个必填字段 |
| 每轮“离线验收通过”（483 tests / 94%），真实环境仍用不起来 | 验收以合成数据和覆盖率为主，从未要求真实闭环跑通 |
| 部署前镜像还没构建完；common 改了却漏列下游服务；只 retry 了 compile 没跑 build | 这些都是可以由工具确定性检查的步骤，却交给了 Agent 的记忆 |

## 3. 决定

1. **重写为 DCE 2.0“缺陷闭环”**，在新分支 `feature/v2-bugfix-loop` 上进行。旧实现打本地 tag `v1.2.0-final` 留在 git 历史，不再维护。
2. **人工确认点只有两个**（用户选择）：
   - G1 修复方案：缺陷描述不清、有多种理解或改动较大时，先给方案等用户确认。
   - G2 合并前：给出 diff 摘要、自审结论和部署计划表，等用户明确同意后才合并到测试分支。
   - 之后的编译、部署、测试、记录、禅道“已解决”自动完成；测试失败自动回到修复循环，再次合并仍要过 G2。
3. **禅道终点是“已解决”**（resolution=fixed，指派回提测人），由测试人员关闭。本期不提供关闭能力。
4. **只覆盖测试环境**。预发/生产只允许输出计划和链接，任何写操作都拒绝。
5. **写操作从“禁止”改为“受控”**：DCE 持有凭证，只开放固定的几条写接口，目标必须落在项目配置里；Agent 不再需要也不允许读取浏览器登录态。

## 4. 保留 / 删除

保留（已在真实平台跑通，迁移到新目录结构）：

- `connectors/http.py`：同源校验、禁止重定向、响应大小上限、重试、日志脱敏。改为“GET + 固定写接口白名单”。
- `connectors/zentao_auth.py`：禅道 v1 Token 登录与单次失效续期。
- `connectors/zentao.py` 的 `bug`、`parse_steps`、`image_content`；`connectors/gitlab.py` 的项目/流水线/Job/Trace；`connectors/portainer.py` 的 Stack/Service/Swarm 信息；`connectors/docker_logs.py`。
- `security/redact.py`、`security/local_credentials.py`（0600 凭证文件加载）、`common/config.py`、`common/errors.py`。

删除：

- 项目模式全部：`project/`（审批 Broker、本机审批页、receipt、Roots 绑定、发现许可）、`project_initialize`。
- 关系图谱与缓存：`catalog/`、`graph/`、`discovery/`、`app/mapping.py`、`ai/`、Schema v1/v2、`schemas/`。
- 旧 MCP 工具（bug_context、project_context、service_trace、pipeline_diagnose、deployment_inspect、discovery_status、三个 `*_query`）和日志授权文件机制。
- `harness/`、`prompts/`、`scripts/`、旧 `docs/`（除 `docs/v2/`）、`PLANS.md` 的历史流水账。git 历史与 tag 足以追溯。

## 5. 刻意不做（防止再次膨胀）

- 不做审批 Broker、本机审批网页、CSRF、receipt、hash 往返、TTL 发现许可。人工确认用对话 + 宿主（Cursor/Codex）自带的工具调用确认。
- 不做关系状态机（proposed/confirmed/stale/conflicted）。配置就是约定，人改文件即确认。
- 不做通用平台查询工具。工具按闭环步骤设计，参数只接受 Bug ID、run ID 和配置里的名字。
- 不做 Nacos、数据库、菜单权限、容器 exec、环境变量修改。这些永远交给人。
- 不做预发/生产部署、不做禅道关闭、不做 MR 审批流。
- 不以离线覆盖率作为完成标准。每个里程碑都要过一次真实环境验收（见 06）。
