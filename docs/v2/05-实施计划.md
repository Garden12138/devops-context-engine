# 05 实施计划（交给 Codex 执行）

> 执行者须知：按 M0 → M5 顺序做，一个任务一个提交。每个任务先写失败的测试，再写实现。每个里程碑结束时停下，把离线结果写进 `docs/v2/progress.md`，并提示用户做该里程碑的现场验收（06 第 2 节）。现场验收通过前，不开始下一个里程碑。

**目标**：把 DCE 重写为支撑“禅道缺陷 → 修复 → 合并 → CI → Portainer 部署 → 测试 → 记录 → 禅道已解决”闭环的 MCP 工具（需求见 02，设计见 03，接口见 04）。

**架构**：platforms（三平台 HTTP 客户端）← workspace（配置、扫描、自检）← loop（计划、合并、构建、部署、缺陷、运行记录）← mcp_server / cli（薄包装）。

**技术栈**：Python 3.12、uv、typer、httpx、pydantic 2、PyYAML、ruamel.yaml、beautifulsoup4、python-dotenv、mcp ≥ 1.30；测试用 pytest、httpx.MockTransport、本地临时 git 仓库。

## 全局约束

- 分支：`feature/v2-bugfix-loop`。只做本地提交，不 push、不建 MR、不改其他分支和 tag（M0 的 tag 除外）。
- 提交信息用 Conventional Commits，例如 `feat(plan): map changed files to modules`。
- 依赖只用上面列出的，新增依赖先问用户。
- 单个源文件不超过 400 行；`mcp_server.py`、`cli.py` 只做参数转换和调用，不写业务逻辑。
- 测试不访问网络：HTTP 用 `httpx.MockTransport`；git 用 `tmp_path` 下的 bare 仓库加 clone。
- 仓库内只能出现合成数据：主机用 `*.example.invalid`，不出现私有 IP、真实仓库名、真实账号。提交前跑 `scripts/check_public_data.py`（pre-commit 钩子已配置）。
- 只实现 02/03/04 写明的东西。文档有矛盾或说不清时，停下来，把问题写进 `docs/v2/progress.md` 的“待确认”一节并告诉用户，不要自行扩展设计。
- **不要**添加审批 Broker、本机审批网页、receipt、hash 校验、Roots 协商、关系状态机、通用平台查询工具。
- 错误信息必须具体（03 第 9 节），禁止把多种失败折叠成一句话。
- 每个任务完成时运行：`uv run pytest -q`、`uv run ruff check .`、`uv run mypy`，全部通过才提交。
- 非测试代码行数按里程碑设预算（见 `CODEX_HANDOFF.md` 第 1.6 节），M5 结束时不超过 6500 行。
- `docs/v2/` 下只允许存在：`README.md`、`01`–`08` 编号文档、`CODEX_HANDOFF.md`、`progress.md`。

### T1.3 CI 解析

接口：`parse_ci(text: str, branch: str) -> CiParseResult`，其中 `CiParseResult` 含 `jobs: list[CiJob]`、`trigger_include: str | None`、`trigger_job: str | None`、`branches_referenced: set[str]`、`modules: list[ModuleGuess]`、`warnings: list[str]`。`ModuleGuess = {path, kind, compile_job, build_job, image}`。规则见 03 第 5.1 节。

在 `tests/fixtures/ci/` 放合成夹具：

- `maven_root.yml`：三个 trigger job，分别对应 master/release/develop，`trigger.include` 指向各自子文件，带 `changes`。
- `maven_dev.yml`：`.compile_template`（rules: develop + changes `demo-modules/$DIR_NAME/**/*` + `when: manual`）、`.build_template`（`export IMAGE_NAME=$MODULE_NAME`；`docker build -t $REGISTRY_DEV/$REPOSITORY/$IMAGE_NAME:latest .`；`docker push ...`）；两个模块，各一对 `compile_x`/`build_x`（`extends` + `variables: DIR_NAME/MODULE_NAME`，build `needs` compile）。
- `web.yml`：全局 `DOCKER_IMAGE: "demo-web"`；`compile_demo_web`（develop manual）；`build_demo_web`（develop on_success，`needs` compile，`docker push $REGISTRY_DEV/$REPOSITORY/$DOCKER_IMAGE:latest`）；另有一个不相关的 `build_other_dev` job。
- `library.yml`：`deploy_common_core`，脚本 `mvn -pl demo-common-core -am deploy`，无 docker。

测试 `tests/test_ci_parser.py`：

- `maven_root.yml` + branch=develop → `trigger_include == ".gitlab-ci-dev.yml"`，`trigger_job == "trigger_dev"`，`branches_referenced == {"master", "release", "develop"}`。

### T3.3 合并

接口：`merge_repo(ws, cfg, run, repo, approved_by_user) -> MergeResult`，步骤见 03 第 6.2 节。

测试 `tests/test_merge.py`（git 夹具）：

- 正常合并：origin 的测试分支出现 merge commit，第二父提交是特性分支，提交信息含缺陷号；用户工作副本的 HEAD 和分支未变；`.dce/tmp` 下没有残留。
- 已合并 → `already_merged`。
- 冲突 → `conflict`，返回冲突文件；origin 测试分支未变；临时 worktree 已删除。
- `approved_by_user=false` → `rejected`。
- 测试分支配置为 `master` → 在 `load_config` 阶段已拒绝；直接调用 `merge_repo` 传入被篡改的配置 → `OUT_OF_SCOPE`。
- 特性分支 worktree 不干净 → `rejected`（GIT_DIRTY）。
- 推送竞争：在 fetch 之后、push 之前（用 monkeypatch 插入），往 origin 测试分支推一个无关提交 → 自动重试一次后成功。
- 测试中检查调用记录，没有任何 `--force` 或 `-f` 参数。

### T3.4 构建

- `gitlab.py`：`pipelines(project, ref, sha)`、`bridges(project, pipeline)`、`jobs_all(project, pipeline)`、`play(project, job)`、`retry(project, job)`、`create_pipeline(project, ref)`、`trace_tail(project, job, lines=200)`。
- `loop/build.py`：`start_builds(ws, cfg, run, items, retry_failed)`、`poll_builds(ws, cfg, run, wait_seconds, clock)`。

测试 `tests/test_build.py`（MockTransport 模拟 GitLab，注入假时钟）：

- direct 模式：compile 为 manual → 调用 play，不 play 同流水线中计划外的 manual job。
- child 模式：从 bridges 取下游流水线。
- 流水线晚 10 秒才出现 → 轮询后找到。
- job 不存在 → 新建流水线 → 找到；新建后仍不存在 → `CI_JOB_MISSING`；同一 run 内不重复新建。
- `retry_failed=true` 时 failed job 被 retry，为 false 时不动。
- 旧构建：build 结束时间早于 compile 开始时间 → `poll_builds` 不算成功并在 `next` 提示；再次 `start_builds` 时该 build 被 retry。
- compile 成功、build 为 manual → `poll_builds` 不发任何写请求，只在 `next` 提示；再次 `start_builds` 时 play 该 build。
- `poll_builds` 全程不发写请求（断言 MockTransport 只收到 GET）。
- digest：Trace 含两次 `digest: sha256:...` → 取最后一个；没有 → `DIGEST_UNKNOWN`。
- 失败分类：每类各一个 Trace 样例，再加一个 unknown。
- `wait_seconds=45` 用假时钟不真正睡眠；状态变化时提前返回。
